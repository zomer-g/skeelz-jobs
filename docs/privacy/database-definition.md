# מסמך הגדרות המאגר — לוח המשרות של SKEELZ

עודכן ב-11.11.2026 (כולל הפרדת התפקידים). טיוטה שמתארת את מה שהמערכת עושה בפועל (תקנה 2 לתקנות הגנת הפרטיות (אבטחת מידע), התשע״ז-2017).
אינה ייעוץ משפטי: עורך דין לפרטיות צריך לאשר את רמת האבטחה של המאגר ואת החובות שנגזרות ממנה.

**המאגר:** מאגר המועמדים והמשרות של לוח המשרות jobs.skeelz.co.il (גרסת xhostd, אפליקציה `skeelz-jobs`).
מקור המידע: המועמדים עצמם (הרשמה, הגשת מועמדות כאורח), מעסיקים ששולחים משרה בטופס הציבורי (`/post-job`), וצוות
SKEELZ (משרות והערות פנימיות).

**מטרות (רשימה סגורה):**
1. פרסום משרות לציבור.
2. קבלת מועמדויות למשרות והעברתן לצוות SKEELZ.
3. יצירת קשר עם מועמדים והתאמתם למשרות.
4. דיוור למועמדים שנרשמו, כשהחיבור למערכת הדיוור פעיל (ראו "החלטות פתוחות" לגבי הסכמה).
5. אבטחת המידע ובירור שימוש חריג (יומן הפעילות).
6. קבלת משרות ממעסיקים בטופס הציבורי, בדיקתן ויצירת קשר עם המעסיק בנוגע אליהן.

**סוגי המידע:**
| קבוצה | שדות |
|---|---|
| מועמדים רשומים | שם פרטי ומשפחה, מייל, טלפון, יישוב, מגדר, תאריך לידה (רשות), כישורים, קובץ קורות חיים (רשות), סיסמה כ-hash (bcrypt), המשרות שהגישו אליהן. מי שנכנס ב"המשך עם Google" (xhostd SSO): גם מזהה קבוע של חשבון ה-Google שלו כפי ש-xhostd מוסר (חשבון שנוצר כך — בלי סיסמה, ובלי טלפון עד שיוסיף) |
| מגישים כאורחים | שם מלא, מייל, טלפון, קורות חיים — לא נשמרים במאגר הזה אלא נשלחים במייל לצוות ול-Salesforce כשהחיבור פעיל; הקובץ נשמר באחסון הקבצים |
| אנשי קשר במשרות | שם, טלפון ומייל של איש הקשר אצל המעסיק — **מוצגים לציבור** כחלק מהמודעה באתר (לא בממשק הציבורי / MCP) |
| מעסיקים ששלחו משרה בטופס | פרטי המשרה; שם, מייל וטלפון של איש הקשר (**לא** מתפרסמים — צוות בלבד); מועד אישור מדיניות הפרטיות; מי טיפל ומתי, סיבת דחייה (רשות). "מייל להגשת מועמדות" וקישור להגשה — רשות, ומתפרסמים במודעה רק אם המשרה אושרה. נמחקים 12 חודשים אחרי האישור/הדחייה (או אחרי השליחה, אם לא טופלה); משרה שאושרה נשארת כמודעה רגילה |
| אנשי צוות (מנהלי תוכן ומנהלי מערכת) | מייל, שם, תפקיד, מזהה הזהות ב-xhostd SSO (נכנסים רק כך, "המשך עם Google"); סיסמה כ-hash רק אם נשמרה מלפני כן (אינה משמשת לכניסה); מועד השבתה, מועד ניתוק חיבורים; סקירות הרשאה |
| יומן הפעילות | מי (מייל של איש צוות, מזהה של מועמד, או כתובת IP של מבקר), מתי, מה, על מה, פרטים (מסננים, מזהי המועמדים שהוצגו). כולל כתובות מייל שהוקלדו בניסיונות כניסה ובבקשות איפוס. שליחת משרה בטופס המעסיקים נרשמת עם כתובת ה-IP ומזהה ההגשה בלבד, בלי פרטי איש הקשר |

מידע רגיש במיוחד במאגר: תאריך לידה ומגדר (שעלולים לשמש להפליה), וקבצי קורות חיים (שעשויים להכיל כל מידע).

**איפה המידע נשמר:**
- מסד נתונים Postgres של ספק האירוח xhostd (ערוץ `prod`), כולל יומן הפעילות.
- קבצי קורות חיים: אחסון קבצים פרטי של xhostd. קובץ שהועלה ולא שויך לאף אחד נמחק אחרי 24 שעות.
- גיבויים: עותק לילי של מסד הנתונים נשמר 7 ימים, ו-3 עותקים לפני כל עדכון גרסה (לפי חבילת xhostd).
- שרתי xhostd עשויים להיות מחוץ לישראל.
- סנדבוקס (אם יוקם): עותק בלי שמות, מיילים, טלפונים, תאריכי לידה וקבצים, אבל עם מגדר, יישוב, כישורים והגשות לכל מזהה.

**מי משתמש במידע (הפרדת תפקידים):**
- מועמד: רק המידע וההגשות של עצמו.
- מנהל תוכן (צוות SKEELZ): ניהול משרות והערות פנימיות, כל המועמדים, ההגשות וקורות החיים — בתוך מגבלה יומית (40 קורות חיים, 1,500 מועמדים) ועם תיעוד מלא. אינו רואה את יומן הפעילות ואינו מנהל הרשאות.
- משרות ממעסיקים: רק מנהלי תוכן בודקים ומאשרים. פרטי איש הקשר מוצגים רק בפתיחת הגשה אחת, וכל פתיחה, עריכה, אישור ודחייה נרשמים ביומן.
- מנהל מערכת (אבטחה): יומן הפעילות, ההתראות, אישורי תוספת, סקירות הרשאה וניהול אנשי הצוות (הוספה, שינוי תפקיד, השבתה, ניתוק חיבורים). **אינו רואה פרטי מועמדים, הגשות או קורות חיים**; ביומן הוא רואה מזהים של מועמדים, מיילים של אנשי צוות, וכתובות מייל שהוקלדו בניסיונות כניסה ובבקשות איפוס.
- לאיש צוות יש תפקיד אחד. מי שצריך את שני התפקידים מקבל שני חשבונות נפרדים.
- מערכת פנימית של SKEELZ (ממשק API פנימי, `/api/internal/v1`): רק דרך מפתח זמני שאיש צוות הנפיק (עד 90 יום, ניתן לביטול)
  או סוד השרת, ורק בהרשאות שהוגדרו לו (משרות, הגשות, מועמדים, קורות חיים, דחיפה ל-Salesforce). אותן מגבלות יומיות
  (40 קורות חיים, 1,500 מועמדים) לכל מפתח בנפרד, ואותו תיעוד מלא.

**העברת מידע:**
| גורם | מה מקבל | מתי |
|---|---|---|
| xhostd | הכול (אירוח) | תמיד |
| xhostd (SSO) ו-Google | "המשך עם Google" (מועמדים ואנשי צוות): xhostd מפעיל את הכניסה מול Google, ו-Google ו-xhostd יודעים שהאדם נכנס לאתר; האתר מקבל מהם מייל, שם ומזהה קבוע. האתר לא שולח להם שום מידע על האדם | כש-`SSO_ENABLED=true` |
| Salesforce של SKEELZ | פרטי מועמדים, הגשות, קורות חיים, משרות | רק כש-`ENABLE_SALESFORCE=true` (כבוי כרגע) |
| מערכות פנימיות של SKEELZ (מפתח API פנימי) | מה שהמפתח מתיר: משרות, הגשות, פרטי מועמדים, קורות חיים | רק כשאיש צוות הנפיק מפתח — מפתח למועמדים, הגשות או קורות חיים רק מנהל תוכן (או הוגדר `INTERNAL_API_SECRET`); כל מסירה נרשמת |

| הציבור — ממשק `/api/public/v1` ושרת MCP `/mcp` (קריאה בלבד, בלי הזדהות) | מודעות משרות פעילות בלבד (כותרת, חברה, תיאור, היקף, תאריך, יישוב וקואורדינטות, כישורים, קישור) — בלי פרטי איש הקשר, בלי מועמדים או הגשות | תמיד |

| Google (Google Analytics 4 דרך Google Tag Manager) | נתוני שימוש בלבד, לפי רשימה סגורה של אירועים ופרמטרים (נספח א'), ומה ש-Google אוספת בעצמה (IP להערכת מיקום — לפי Google לא נרשם ולא נשמר ב-GA4; מכשיר, דפדפן, מזהה עוגייה אקראי). **לא** שם, מייל, טלפון, קורות חיים, שם קובץ או טקסט שהוקלד | רק אם הוגדרו `GTM_ID` / `GA_ID` (לא מוגדרים), ורק אחרי שהמבקר אישר בבאנר: לפני כן הקוד של Google לא נטען כלל (Consent Mode v2, ברירת מחדל: חסום). פרסום — תמיד חסום. Google מעבדת גם מחוץ לישראל (בין השאר ארה"ב) |

**הסיכונים העיקריים:**
1. גישה לא מורשית לחשבון של איש צוות — אנשי צוות נכנסים רק דרך xhostd SSO (חשבון Google, עם האימות הדו-שלבי של Google אם הופעל בו); סיסמה שדלפה אינה מספיקה.
   וגם מפתח API פנימי שדלף — מוגבל בזמן, בהרשאות ובמגבלה היומית, וניתן לביטול מיידי.
2. שימוש חורג של מנהל תוכן מורשה: משיכה המונית של מועמדים או קורות חיים.
3. מנהל מערכת שנותן לעצמו גישה למועמדים דרך חשבון נוסף בתפקיד מנהל תוכן. כל שינוי תפקיד נרשם ביומן ונבדק בסקירת ההרשאות. מפתח API פנימי עם הרשאה למועמדים, להגשות או לקורות חיים מנהל מערכת לא יכול להנפיק כלל (השרת דוחה, לפי התפקיד במסד הנתונים, והניסיון נרשם); רק מנהל תוכן מנפיק מפתח כזה.
4. חשיפה דרך ספק (xhostd, Salesforce, SMOOV).
5. קבצים זדוניים שמועלים בידי אנונימיים.
6. מגדר ותאריך לידה כבסיס להפליה בסינון מועמדים.
7. הצפה של טופס המעסיקים בהגשות (ספאם) או ניסיון להחדיר תוכן זדוני למודעה — מגבלה לכל כתובת IP, מלכודת בוטים, תקרה למספר ההגשות הממתינות, טקסט רגיל בלבד, ואישור ידני לפני פרסום.
ההתמודדות — בנוהל אבטחת המידע (`security-procedure.md`).

## נספח א' — מדידת שימוש (Google Analytics 4)

**איך זה עובד:** Google Analytics 4 נטען דרך Google Tag Manager, רק כשהוגדרו `GTM_ID` / `GA_ID`. באנר עוגיות
(עברית/אנגלית) מבקש הסכמה. לפני הסכמה: מצב Consent Mode v2 = denied לכל הסוגים, הקוד של Google **לא נטען**, אין
עוגיות ולא נשלח דבר. אחרי הסכמה: הקוד נטען ונשלחים רק האירועים שבטבלה (רשימה סגורה בקוד:
`client/src/utils/analyticsPolicy.ts`; כל פרמטר אחר, או ערך שנראה כמו מייל/טלפון, נמחק לפני השליחה). הסכמה לפרסום
תמיד חסומה. אותה רשימה מוצגת בעמוד `/privacy`; `server/test/analytics.test.ts` נכשל אם הם לא תואמים.

**לא נשלח לעולם:** שם, מייל, טלפון, תאריך לידה, קובץ קורות חיים או שמו, טקסט חופשי (טפסים, תיאור משרה, חיפוש),
מיקום שנבחר במפה, סיסמאות וקודי איפוס, הודעות שגיאה (רק קוד ושם שדה).

בכל אירוע נשלחים גם: `page_path`, `page_location`, `page_referrer`, `language`, `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`.
